== What an operator is

An operator is generally a process handling _Custom Resource Definition_ (CRD).
In other words, it is a process handling custom descriptor types.

A common example is to handle an `API` kind of descriptor instead of creating a `ConfigMap` plus a `Deployment` plus an `Ingress` plus a `LoadBalancer`:

[source,yaml]
----
apiVersion: custom.company.com/v1
kind: MyAPI
metadata:
  name: my-api
  namespace: my-apps
spec:
  path: /api/my
  image: company/my-api:1.0
----

NOTE: as for Yupiik Bundlebee, we prefer to use descriptors in JSON since it is easier to work with and less error prone.

Once deployed, the operator will be responsible to convert the `spec` in Kubernetes default objects (`Deployment`, ...).
On the user side you can manage your API with any Kubernetes API client, including `kubectl`: `kubectl get -n my-apps my-apis`.

== Configuration

The operator default runtime has these default configuration keys:

[opts="header",cols="^,^,^"]
|===
| Key | Default | Description
| `operator.enabled` | `true` | Enable watches and probes; set explicitly to `false` for metadata-only or disabled containers.
| `operator.kubernetes.master` | from `KUBERNETES_SERVICE_HOST`/`PORT` | The Kubernetes API master URL.
| `operator.kubernetes.tls-skip` | `false` | Skip TLS validation.
| `operator.kubernetes.token` | `/var/run/secrets/kubernetes.io/serviceaccount/token` | The service account token.
| `operator.kubernetes.certificates` | `.../ca.crt` | The cluster CA certificate.
| `operator.use-bookmarks` | `true` | Use bookmarks in previews.
| `operator.event-thread-count` | `1` | Number of event dispatch threads.
| `operator.probe-port` | `8081` | Port of the probe/health server.
| `operator.await` | `true` | Await the operator before the container exits.
| `operator.storage` | - | Directory for the last processed resource inventory, used to detect downtime deletions; startup always lists current API state.
| `operator.retry.initial-delay` | `100` | Initial list/watch retry delay in milliseconds (at least 1).
| `operator.retry.max-delay` | `5000` | Delay cap in milliseconds, at least the initial delay; also caps `Retry-After`.
| `operator.retry.retry-permanent-errors` | `false` | Retry permanent API or invalid-response failures instead of stopping the affected watch.
|===

`Operator.DefaultOperatorConfiguration` (reusable in custom `@RootConfiguration` records) exposes `namespaced` (`true`), `namespaces` (`["default"]`), `resource-plural-name` (required) and `api-version` (required).

=== Activation and probes

Operators start by default, including when the module is discovered in a container used only for metadata.
Such containers must set `operator.enabled=false` explicitly.
This switch is checked before resolving typed operator configuration, Kubernetes clients, executors, operator instances or probes, so a disabled container does not require valid Kubernetes settings or an available probe port.

The existing probe server exposes `GET /health` for liveness and `GET /ready` for initial-inventory/terminal-failure readiness.
Readiness returns 503 until every configured watch has reconciled a complete fresh API list, and after any watch stops terminally.
It returns 200 after initial synchronization, including during transient reconnects; it is not a freshness or Kubernetes connectivity guarantee.
Liveness and `/metrics` are unchanged.
Startup still waits for operator `onStart`, not for Kubernetes list/watch success, so configure a readiness probe if deployment activation must reflect synchronization failures.

=== Recovery and delivery

Transport failures, HTTP 408/429/5xx and normal stream EOF reconnect with exponential backoff capped by `operator.retry.max-delay`.
Valid events reset the backoff; merely opening an empty stream does not.
For 429/503, numeric or HTTP-date `Retry-After` is honored within the configured cap; malformed or past values are ignored.
Kubernetes `Status` failures are also checked in HTTP-200 list responses, bare watch Status responses and in-band `ERROR` events.
Status `details.retryAfterSeconds` is supported for 429/503.
Cancellation during shutdown is quiet and does not schedule another request.
Diagnostics identify the runtime logger, watch index, list/watch phase, status and retry delay, with repeated failures sampled; response bodies, resource contents, URLs and exception details are not logged.

By default, permanent API failures (notably 401, 403 and collection 404), invalid list responses and callback failures stop only the affected collection/namespace watch.
Other watches and operators keep running, the process stays alive, and readiness becomes unsuccessful.
There is no process exit or automatic shutdown of unrelated operators.
Correct the configuration/permissions/handler and restart the application to recover a terminal watch.
Set `operator.retry.retry-permanent-errors=true` when API or schema provisioning is expected to recover without a restart; it does not retry failed application callbacks.
HTTP or in-band 410 discards the expired cursor and performs a complete relist, reconciling deletions only within that watch's known inventory.

Every startup performs a fresh full LIST of current API objects, regardless of stored or expired resource versions.
There is no startup `limit=1` cursor-validation probe: it cannot supply current reconciliation values and would allow stale persisted additions before downtime changes are discovered.
All continuation pages must share the same collection `metadata.resourceVersion` and are collected before delivering callbacks, comparing deletions or persisting inventory.
Lists without a nonblank collection resource version, with inconsistent page versions or with malformed continuation tokens are invalid responses, not successful synchronization or the end of pagination.
The complete list must also contain unique, nonblank item UIDs and, for namespace-specific watches, objects belonging to the watched namespace; an invalid identity rejects the entire snapshot before callbacks.
The runtime delivers `onAdd` for the current listed objects before opening WATCH from the LIST collection's `metadata.resourceVersion`; resource versions are opaque tokens, never a maximum of individual object versions.
A failed startup LIST does not replay stale objects, publish a partial snapshot, open that watch or make it ready.
Live reconnects use the last successfully processed in-memory event or bookmark cursor; 410 requires another complete current LIST.

Storage writes only the companion `.items` JSON inventory by atomic replacement where supported, after successful callbacks.
The existing inventory shape (including informational metadata) is retained for upgrade compatibility, but only validated item UIDs and their old object data are used to identify downtime deletions absent from the fresh snapshot, including when it is empty.
Persisted objects are never replayed through `onAdd`, and no persisted startup cursor is read, validated or resumed.
Legacy cursor files are ignored and no longer written; they may be removed, while keeping `.items` preserves downtime deletion comparison during upgrades.
Missing or corrupt inventory safely starts from current API state, without historical deletion comparison.
An inventory with duplicate/missing UIDs or objects outside the watched namespace is ignored as a whole, so reusing storage after a namespace change cannot emit deletions for the previous namespace.
Downtime deletions are delivered before current additions, comparing UIDs rather than names so a recreated object deletes the old identity and adds the new one.
Callbacks run before inventory persistence and the next watch connection; if a callback throws, only the affected watch stops.
Inventory I/O failures are diagnosed but do not roll back successful callbacks, the in-memory cursor or readiness; an outdated inventory can therefore miss downtime deletions or repeat deletion callbacks on a later restart.
Crash recovery can repeat callbacks; filesystem atomic replacement is not a power-loss durability guarantee.
Do not share a storage directory between simultaneous processes or distinct operators using the same resource plural name.

NOTE: Make `onAdd`, `onModify` and `onDelete` idempotent: restart, relist and server replay can repeat work, and the runtime does not promise exactly-once external side effects or suppress same-version callbacks.

=== Event workers and shutdown

The scheduler supplied to the runtime/controller is borrowed for HTTP work and retry timers and is never closed by the controller.
Event callbacks run on a separate, controller-owned worker pool sized by `operator.event-thread-count`, so blocked callbacks do not consume scheduler threads.
The controller has two ingress lanes: the legacy raw event queue and internal tasks, each FIFO, alternating when both have work to avoid starvation.
There is no global ordering between lanes, and with multiple workers callback completion order is unspecified; the runtime separately preserves each watch's callback/checkpoint order and yields between bounded batches.
The protected raw queue remains a real unbounded `BlockingQueue` supporting direct `offer`, `put` and `add`; `onEvent` is preferred for admission synchronized with shutdown.
Controller diagnostics for this legacy ingress also omit raw event bodies and exception details; `onError` still receives the original ERROR event.
Shutdown closes admission, cancels watches/retry timers and drains accepted work for up to five seconds before discarding pending work and interrupting only the owned workers.
Direct raw queue writes after the shutdown snapshot are not processed.
The five-second bound covers the worker drain, not application `onStop` code or callbacks that ignore interruption; borrowed clients and schedulers remain application/container-owned.

== Build a custom operator

As soon as you imported `fusion-kubernetes-operator-base` module (and as any Fusion application you can use `fusion-api` and build dependencies `fusion-processor` and `fusion-build-api`) you have to implement the `Operator` API and define your custom resource model (`spec`).

This API enables you to get current state of the descriptors (it starts by a "find all") and listen for any change (add, modify, delete hooks).

TIP: there is an `Operator.Base` class which enables to ease the configuration and a `BulkingOperator` which gives you events by bulk instead of one by one to bulk changes and reduce the work you do with the API when needed.

Here is an operator just logging custom resource events - the other actions are generally custom:

[source,java]
----
@ApplicationScoped
public class APIOperator extends Operator.Base<APIResource> { //  <1>
    private final Logger logger = Logger.getLogger(getClass().getName());

    private final KubernetesClient kubernetes;
    private final JsonMapper jsonMapper;

    public APIOperator(
            // <2>
            final KubernetesClient client, final JsonMapper jsonMapper) {
        super(
                APIResource.class, // <3>
                // <4>
                new DefaultOperatorConfiguration(true, List.of("default"), "api", "company.com/v1"));
        this.kubernetes = client;
        this.jsonMapper = jsonMapper;
    }

    @Override
    public CompletionStage<?> onStart() { // <5>
        logger.info(() -> "Starting operator " + getClass().getName());
        return super.onStart();
    }

    @Override // <6>
    public void onAdd(final APIResource object) {
        logger.info(() -> "[ADD] " + object);
    }

    @Override // <6>
    public void onDelete(final APIResource object) {
        logger.info(() -> "[DELETE] " + object);
    }

    @Override // <6>
    public void onModify(final APIResource object) {
        logger.info(() -> "[MODIFY] " + object);
    }
}
----
<.> We inherit from `Operator.Base` to simplify the implementation (fully optional),
<.> We inject the kubernetes client (generally to do the `Deployment` or other resources creation),
<.> We define our custom model type for our resource/CRD,
<.> We define the name we register for our CRD (see later),
<.> On startup we have a callback before watching events giving us the opportunity to query the same of the mapping between the CRD and actual instance (the deployment behind an API for example) to be able to update it easily later on,
<.> Finally we listen for CRD changes and adjust our actual runtime on it.

=== Creating a container for our operator

You can create the image of your container as you want but the easiest is to use `jib` or Geronimo Arthur maven plugins.

Here is how with JIB I can convert my module to a container:

[source,xml]
.In plugins section of my pom.xml
----
<plugin>
  <groupId>com.google.cloud.tools</groupId>
  <artifactId>jib-maven-plugin</artifactId>
  <version>3.3.2</version>
  <configuration>
    <containerizingMode>packaged</containerizingMode>
    <from>
      <image>ossyupiik/java:17.0.7@sha256:1a08a09ea4374243f28a48ec5331061d53abcdac70e51c1812b32ac4055a7deb</image>
    </from>
    <to>
      <image>company/operator-api:latest</image>
    </to>
    <container>
      <mainClass>io.yupiik.fusion.framework.api.main.Launcher</mainClass>
      <appRoot>/opt/company/api-controller</appRoot>
      <workingDirectory>/opt/company/api-controller</workingDirectory>
      <jvmFlags>
        <jvmFlag>-XX:+ExitOnOutOfMemoryError</jvmFlag>
      </jvmFlags>
    </container>
  </configuration>
</plugin>
----

TIP: it is recommended to add the following dependency to your pom:

[source,xml]
----
<dependency>
  <groupId>io.yupiik.logging</groupId>
  <artifactId>yupiik-logging-jul</artifactId>
  <version>${yupiik-logging.version}</version>
  <scope>runtime</scope>
</dependency>
----

and then in your `jvmFlags` add (to get logs in JSON):

[source,xml]
----
<jvmFlag>-Djava.util.logging.manager=io.yupiik.logging.jul.YupiikLogManager</jvmFlag>
<jvmFlag>-Dio.yupiik.logging.jul.handler.StandardHandler.formatter=json</jvmFlag>
----

Once done, you can run `mvn package jib:build` to push the image to the remote registry if set or `mvn package jib:dockerBuild` to push it to your docker daemon.

=== Deploy your operator

Before deploying your operator, you need to define your CRD, this is done in a yaml or JSON file and defines the API your operator will support.

TIP: for a full reference, refer to Kubernetes documentation.

Here is an example for the API CRD we took as an example:

[source,json]
.crd.json
----
{
  "apiVersion": "apiextensions.k8s.io/v1",
  "kind": "CustomResourceDefinition",
  "metadata": {
    "name": "apis.company.com"
  },
  "spec": {
    "group": "company.com",
    "versions": [
      {
        "name": "v1",
        "served": true,
        "storage": true,
        "schema": {
          "openAPIV3Schema": {
            "type": "object",
            "properties": {
              "spec": {
                "type": "object",
                "properties": {
                  "image": {
                    "type": "string"
                  },
                  "path": {
                    "type": "string"
                  }
                }
              }
            }
          }
        },
        "additionalPrinterColumns": [
          {
            "name": "Path",
            "type": "string",
            "description": "Path of the endpoint",
            "jsonPath": ".spec.path"
          },
          {
            "name": "Image",
            "type": "string",
            "description": "Image of the main container containing the API",
            "jsonPath": ".spec.image"
          },
          {
            "name": "Age",
            "type": "date",
            "jsonPath": ".metadata.creationTimestamp"
          }
        ]
      }
    ],
    "scope": "Namespaced",
    "names": {
      "plural": "apis",
      "singular": "api",
      "kind": "API"
    }
  }
}
----

Once this descriptor applied (using `mvn bundlebee:apply` or `kubectl apply`), you can deploy the operator itself.
The operator requires a service account with `list` and `watch` permissions on the watched resources; pagination requires no additional permission.
Grant `get` or write permissions only when your handlers use those operations, for example to fetch individual resources or create/update/delete deployments or ConfigMaps.

TIP: Use a `Role` and `RoleBinding` for each watched namespace; watching across all namespaces or watching cluster-scoped resources requires a `ClusterRole` and `ClusterRoleBinding`.

TIP: you can also use `@CustomResourceDefinition` to generate a default descriptor in your jar:

[source,java]
----
@CustomResourceDefinition(
        group = "test.yupiik.io",
        name = "MyCrd",
        description = "",
        shortNames = "mcrd",
        spec = MyOperator.MySpec.class,
        status = MyOperator.MyStatus.class,
        selectableFields = ".spec.type",
        additionalPrinterColumns = @CustomResourceDefinition.PrinterColumn(name = "Type", jsonPath = ".spec.type", type = "string"))
public class ....
----

NOTE: we decided to not generate the role/cluster role since except the default `list` and `watch` (optionally `status`) permissions on your CRD,
it 100% depends on what you're doing so would be 1-1 with defining the role.

==== Creating the service account

NOTE: this part is mainly to give you an entry point but it will need customization depending your case.

The service account part will be composed of:

* A service account we will use in the controller,
* A role (list of roles actually) giving the permission to the kubernetes client to do what is needed,
* A role binding to associate the role to the service account.

Here is the service account:

[source,json]
.serviceaccount.json
----
{
  "apiVersion":"v1",
  "kind":"ServiceAccount",
  "metadata":{
    "name":"api-controller",
    "namespace":"default",
    "labels":{
      "app":"api-controller"
    }
  }
}
----

IMPORTANT: you can need to create one per namespace you target - or let your operator doing it using another service account but this is out of scope of this part.

The role will require at minimum the list and watch permissions on your custom resource:

[source,json]
.role.json
----
{
  "apiVersion": "rbac.authorization.k8s.io/v1",
  "kind": "Role",
  "metadata": {
    "name": "api-controller",
    "namespace": "default",
    "labels": {
      "app": "api-controller"
    }
  },
  "rules": [
    {
      "apiGroups": [
        "company.com"
      ],
      "resources": [
        "apis"
      ],
      "verbs": [
        "list",
        "watch"
      ]
    }
  ]
}
----

Finally, the role binding associates both:

[source,json]
.rolebinding.json
----
{
  "apiVersion": "rbac.authorization.k8s.io/v1",
  "kind": "RoleBinding",
  "metadata": {
    "name":"api-controller",
    "namespace":"default",
    "labels":{
      "app":"api-controller"
    }
  },
  "subjects": [
    {
      "kind": "ServiceAccount",
      "name": "api-controller"
    }
  ],
  "roleRef": {
    "kind": "Role",
    "name": "api-controller",
    "apiGroup": "rbac.authorization.k8s.io"
  }
}
----

==== Deployment for the controller

The controller can be a deployment or statefulset if you need to store some state:

[source,json]
.deployment.json
----
{
  "apiVersion": "apps/v1",
  "kind": "Deployment",
  "metadata": {
    "name": "api-controller",
    "namespace": "default",
    "labels": {
      "app": "api-controller"
    }
  },
  "spec": {
    "selector": {
      "matchLabels": {
        "app": "api-controller"
      }
    },
    "template": {
      "metadata": {
        "labels": {
          "app": "api-controller"
        }
      },
      "spec": {
        "serviceAccountName": "api-controller", <1>
        "automountServiceAccountToken": true,
        "containers": [
          {
            "name": "operator-controller",
            "image": "company/operator-api",
            "readinessProbe": { <2>
              "initialDelaySeconds": 4,
              "periodSeconds": 30,
              "failureThreshold": 10,
              "timeoutSeconds": 20,
              "httpGet": {
                "path": "/health",
                "port": 8081
              }
            },
            "livenessProbe": { <2>
              "initialDelaySeconds": 5,
              "periodSeconds": 30,
              "failureThreshold": 10,
              "timeoutSeconds": 30,
              "httpGet": {
                "path": "/health",
                "port": 8081
              }
            }
          }
        ]
      }
    },
    "replicas": 1 <3>
  }
}
----
<.> Don't forget to mount the service account which has the right roles for the controller/operator,
<.> If you didn't disable the operator probes, you can setup health checks - optional since in case of error the operator should crash,
<.> By default there is no leader election so a single instance is needed but if you handle it you can scale - but generally it is not needed since scalability is in the instances you create, not there until you are a cloud provider.

== Operator and persistence

If you configure the `storage` property, each collection/namespace watch persists its known resource inventory in a `.items` file for downtime deletion comparison.
Startup always lists fresh API state before delivering additions and watching at the fresh collection version; persistence does not enable persisted-cursor resume or stale startup additions.

The inventory is checkpointed after successful list reconciliation and resource events.
Bookmarks advance the in-memory reconnect cursor without rewriting unchanged inventory.

The persistence is on the local storage so implies a single replica of the operator as of today.

TIP: you can disable, in the configuration, the probes, this is to ease to embed the operator stack in a custom `fusion-http-server` based module which will implement the probes itself.
