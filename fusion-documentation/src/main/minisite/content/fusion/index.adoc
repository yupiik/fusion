[abstract]
Fusion framework aims at providing a very light framework.

== Core Values

For cloud applications, being the most reactive possible is a key criteria so Fusion chose to:

* Be build time oriented: only delegate to runtime the bean resolution (to enable dynamic module aggregation) and not the bean and model discovery nor proxy generation,
* Stay flexible: even if the model is generated at build time you can generally still customize it by removing a bean and adding your own one,
* Be native friendly: some applications need to be native to start very fast and bypass the classloading and a bunch of JVM init, for that purpose we ensure the framework is GraalVM friendly - using Apache Geronimo Arthur or not.

== Features

Fusion is a full framework: at its core it is an Inversion-of-Control (IoC) container and event bus, and around it a set of opt-in modules cover the cloud application stack. Everything users mark and use is generated at build time, so the runtime only resolves already-known beans - this is what makes it fast, lightweight and GraalVM native friendly.

=== Core container

* Field and constructor injections
* Contexts/scopes
** Default scope (`@DefaultScoped`) creates an instance per lookup/injection
** Application scope (`@ApplicationScoped`) creates an instance per container and instantiates it lazily (at first call)
* Event bus with a synchronous, `@Order`-sorted dispatch:
** `Start`/`Stop` events fired around the container lifecycle,
** any custom event via the injected `Emitter`.
* Lifecycle: `@Init`/`@Destroy` to react to the bean lifecycle; a method-produced bean returning an `AutoCloseable` is `close()`d on destroy
* `Optional<MyClass>`, `List<T>` and `Set<T>` injections, with `@Order` to sort or to override a single injection
* Type-safe, source-ordered cloud friendly configuration (see cross the xref:examples.adoc#configuration_model[configuration example])
* Module aggregation through the `FusionModule` SPI (auto-discovered via `ServiceLoader`), with filters/mappers to replace beans, contexts and listeners
* Manual interception and function composition with the xref:examples.adoc[`Wraps`] utility (no declarative interceptors)
* `Launcher`/`CliLauncher` mains for plain JVM or CLI entry points

=== Opt-in modules

* xref:json.adoc[JSON] - reflectionless records mapping, JSON-Pointer/Patch/diff, JSON Schema validation and Draft 2020-12 conversion
* xref:http-server.adoc[HTTP server] - Apache Tomcat abstraction with `Endpoint`/`@HttpMatcher`, health checks and metrics
* xref:http-client.adoc[HTTP client] - extended `java.net.http` client with listeners, routing, throttling and HAR/NDJSON replay
* xref:jsonrpc.adoc[JSON-RPC] - JSON-RPC 2.0 over HTTP with OpenRPC discovery
* xref:persistence.adoc[Persistence] - reflectionless JDBC entity mapping with multiple dialects
* xref:kubernetes-client.adoc[Kubernetes client] - light in-cluster client
* xref:kubernetes-operator.adoc[Kubernetes operator] - watch/reconcile runtime to build operators
* xref:tracing.adoc[Tracing] - Zipkin/OpenTelemetry oriented tracing for server and client
* xref:jwt.adoc[JWT] - signing and validation on the JDK with no extra dependency
* xref:handlebars.adoc[Handlebars] - dependency-free templating
* xref:cli.adoc[CLI] - simple command-line applications from `@Command` beans
* xref:testing.adoc[Testing] - JUnit 5 integration with container lifecycle and `TestClient`
* xref:documentation.adoc[Documentation] - generate Asciidoc/OpenAPI/Postman from the generated metadata
* xref:ai-skills.adoc[AI skills] - installable coding-agent skills for opencode and Claude

== Limitations

NOTE: these are limitations _as of today_, none are _technically_ strong limitations we can't fix at a later point if desired.

* A no-arg constructor must be available for beans using a subclass proxy scope (like `@ApplicationScoped`) - it is not required for `@DefaultScoped` beans nor for method-produced beans,
* Event methods can not be package scope if the enclosing bean uses a subclass proxy (like `@ApplicationScoped` context),
* Constructor injections are supported but for proxied scopes (`@ApplicationScoped` for ex) it requires a default no-arg constructor (in scope `protected` or `public`) in the class (if not existing the instantiation constructor will be called with null parameters),
* Event bus listeners can only have the event as method parameter,
* Only classes are supported exception for method producers which can return a `ParameterizedType` (ex: `List<String>`) but injections must exactly match this type and `List`/`Set` injections are handled by looking up all beans matching the parameter,
* Generic class beans (ex: `class MyService<X>`) are registered with their raw type, a parameterized injection or lookup of the same class (ex: `MyService<String>`) matches this bean whatever the type arguments are.
